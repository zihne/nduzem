# ADR-0002: M3.3 — Play Billing client integration

- **Status**: Accepted
- **Date**: 2026-07-02
- **Related**: server ADR-0033 (IAP foundation),
  server ADR-0034 (Google Play real verification),
  [ADR-0001](0001-m1-client-architecture.md) (client stack)

## Context

The client-side M3.3 foundation (server merged separately) added a
paywall screen that talks to `/v1/billing/iap/verify` with synthetic
`STUB:<sku>:<txn>` receipts. That let us test the plumbing end-to-end
without any store integration, but it never talks to Play Billing —
tapping Buy skips right past the Play Store dialog.

Now that the server accepts real Play purchase tokens (server ADR-0034),
the client needs to actually initiate a Play Billing purchase, capture
the resulting `purchaseToken`, POST that to `/iap/verify`, and
acknowledge back to Google on success.

Design questions worth recording:

1. **Which plugin?** `in_app_purchase` (Google official Flutter
   plugin) covers both StoreKit and Play Billing behind a unified
   Dart API — but that unification hides some platform differences
   we care about (Play's `purchaseToken` vs StoreKit's JWS).
2. **iOS/desktop/web behaviour when there's no Play?** We haven't
   built Apple live verification yet (server-side stub). If a user
   opens the paywall on iOS, do we hide Buy, refuse, or fall back
   to the stub-receipt path?
3. **Where does the purchase state machine live?** Play Billing is
   inherently async — a purchase is a stream of updates, not a
   blocking call. The paywall is a screen that mounts/unmounts.
4. **Product ID mismatch between Play Console and the server
   catalog?** The server catalog owns the SKU strings; Play Console
   is where the operator registers matching product IDs. What
   happens when they drift?
5. **Consumables vs subscriptions.** `in_app_purchase` treats them
   as different flows (`buyConsumable` vs `buyNonConsumable`;
   subscriptions go through `buyNonConsumable` in the current API).
   The plugin's semantics here have gotchas.

## Decision

### Plugin: `in_app_purchase` (Google official)

Add `in_app_purchase: ^3.2.0` to `pubspec.yaml`. Reasons:

- Official, maintained by Google, ships with both platform impls
  built in.
- The alternative (`flutter_inapp_purchase` etc.) don't have the
  same Google-backed support cadence, which matters on a payments
  code path where a broken plugin release blocks revenue.
- We already accept the "unified Dart API" tradeoff — the underlying
  `PurchaseDetails.verificationData.serverVerificationData` field
  gives us exactly what we send to the server (Play `purchaseToken`
  on Android, base64 receipt on iOS), regardless of platform.

### Platform behaviour

- **Android with Play Store available** → real Play Billing flow.
  Buy triggers `InAppPurchase.instance.buyConsumable(...)` (credit
  packs) or `buyNonConsumable(...)` (subscriptions). Purchase stream
  delivers a `PurchaseDetails` with the token. We send the token to
  `/iap/verify`, then acknowledge via `completePurchase`.
- **Android without Play Store** (rare — rooted / stripped devices)
  → fall back to the STUB path. The server accepts `STUB:*` receipts
  regardless of platform (per server ADR-0033), and the paywall is
  clearly labelled as dev-mode when this happens.
- **iOS** → STUB path for now. Server-side Apple live verification
  isn't wired up yet (server ADR-0033 open follow-up
  `feat/m3.3-apple-verify`), so a real StoreKit purchase would just
  bounce off a 501. Rather than hide the paywall entirely on iOS,
  keep it functional via stubs and swap the platform check when
  Apple lands.
- **Desktop / web** → STUB path. Not shipping targets yet, but the
  build doesn't have to break.

The platform decision lives in one predicate: `_playAvailable()`.
Everything downstream branches on it.

### Purchase state machine lives in a service, not the screen

`IapPurchaseService` owns:

- Plugin initialization (once per app lifetime, via a Riverpod
  provider).
- The purchase stream subscription.
- A `Future<IapPurchaseOutcome> buy(sku, productType)` API that
  starts a purchase and completes when the stream emits the
  matching PurchaseDetails.
- Server verification + `completePurchase` acknowledgement.

Rationale: the paywall screen can be disposed (user backs out,
system reclaims memory) while a purchase is in flight — Play Billing
delivers updates via the stream regardless of screen lifecycle, and
we'd otherwise leak the acknowledgement or drop the token. Holding
the state machine in a Riverpod service that outlives any single
screen removes the whole class of "purchase completed but screen was
gone" bugs.

The screen just calls `service.buy(...)` and awaits — the service
handles the stream plumbing under the hood.

### Product ID convention

Server SKUs (`credit_starter`, `sub_personal`, …) must match Play
Console product IDs **exactly**. We already document this in the
server's `PLAY_CONSOLE_SETUP.md`. On the client:

- On paywall mount, we `queryProductDetails({...serverCatalogSkus})`
  against Play.
- Any SKUs that come back in `notFoundIDs` are surfaced in the UI
  as "not available on this device" and the Buy button is disabled
  for them.
- Server-catalog prices are shown as-is; we do NOT overwrite them
  with the Play-reported price (Play's price is the source of truth
  for the actual charge, but the catalog is authoritative for what
  the user sees pre-purchase — see server ADR-0011 for why). We
  DO cross-check that the two are consistent and log a warning
  when they drift.

### Consumable vs subscription

For `credit_pack` products we use `buyConsumable(autoConsume: false)`.
The plugin's default of `autoConsume: true` consumes on delivery,
which would prevent our server verification path from running against
the token — the token becomes stale as soon as Play consumes. We
consume manually via `completePurchase` **after** the server has
successfully verified.

For `subscription` products we use `buyNonConsumable`. Subscriptions
are inherently non-consumable (they don't get "used up"); Play's
renewal-notification pipeline (server RTDN follow-up) handles the
recurring grants server-side, not via re-purchase.

### Server verification handshake

The purchase flow, end-to-end:

1. User taps Buy → `service.buy(sku, productType)`.
2. Service calls `InAppPurchase.instance.buyConsumable(...)` or
   `buyNonConsumable(...)`.
3. Play dialog appears; user completes / cancels / errors.
4. Purchase stream delivers `PurchaseDetails`.
5. If `status == purchased`: extract
   `verificationData.serverVerificationData` (Play `purchaseToken`)
   and POST to `/iap/verify` with the SKU + region.
6. On server success: call
   `InAppPurchase.instance.completePurchase(purchaseDetails)`. This
   acknowledges to Play (mandatory within 3 days — otherwise Play
   auto-refunds) and consumes credit-pack tokens.
7. Return the updated balance to the caller.

**If server verification fails**: DON'T `completePurchase`. Play will
re-deliver the purchase in the stream on next app open, giving us
another chance to verify. If the failure is 501 (server-side
misconfig), we surface a clear error message; if it's 502 (transient),
we retry once transparently before surfacing.

**If Play refuses to deliver a token** (network, dialog dismissal,
user canceled): surface as user-facing error, no server call.

## Consequences

- **Real Play Billing purchases now work on Android** with the
  operator-provided Play Console setup.
- **iOS / desktop / web keep working via stubs** so the paywall
  isn't gated on Apple live verification landing.
- **The state machine survives screen disposal**, so acknowledgement
  and server verification always complete — no orphaned purchases.
- **Play Console + server catalog SKU mismatches surface loudly**
  rather than silently degrading — the paywall tells the user which
  products aren't available on this device, and dev logs record the
  mismatched IDs.
- **Manual consumption (`autoConsume: false`)** means a crash between
  Play delivering the purchase and us verifying/acknowledging leaves
  the purchase in Play's queue. On next app open, the stream
  redelivers it — we verify (server idempotency handles the retry
  correctly per server ADR-0033) and acknowledge. Zero data loss.
- **No new native code.** `in_app_purchase` bundles the platform
  channels. Android `com.android.vending.BILLING` permission is
  merged in automatically by the plugin's manifest — no manifest
  edits needed for v3.x.
- **Deploy size grows by ~1 MB** (Play Billing Library shipped by
  the plugin). Acceptable — this is a revenue path.
- **The stub receipt path stays alive on Android as a fallback**
  when Play isn't available. Rare in practice but keeps the paywall
  UX usable in every environment.

## Alternatives considered

- **Roll our own Play Billing FFI.** The Play Billing Library is
  Java/Kotlin, so we'd need method channels + a lot of glue. Rejected
  — `in_app_purchase` already does exactly this, correctly.
- **Only ship on Android; hide the paywall on iOS.** Would work but
  the paywall is useful on iOS during development (stub-mode) and
  we don't want to gate the UI on Apple live landing. Keep it live
  with stubs.
- **Put the purchase state machine in the paywall screen.** Simpler
  wiring, but any screen dismissal mid-purchase leaks the purchase
  (we'd never acknowledge, and Play would eventually re-deliver
  with no listener attached). Service ownership is worth the
  ceremony.
- **`autoConsume: true` (the plugin default).** Simpler code path
  but consumes the token before our server can verify it — Google's
  own docs recommend verifying server-side BEFORE consuming, so
  `autoConsume: false` is correct here.
- **Rely purely on Play's client-side receipt.** Would skip the
  server round-trip and grant credit optimistically. Rejected —
  server verification is the whole point of the M3.3 architecture
  (spec §9.6 / server ADR-0034); trusting the client for revenue
  events is not the pattern.
- **`storekit_purchase` / `flutter_inapp_purchase`.** Alternate
  Flutter plugins with similar surfaces. Rejected on maintenance
  cadence — Google's official plugin gets Play API updates in step
  with the platform.

## Open follow-ups

- **`feat/m3.3-apple-verify`** (server-side) then a client swap of
  the iOS stub-receipt path for real StoreKit v2 receipts.
- **`feat/m3.3-play-notifications`** (server-side) — RTDN webhook
  for renewals / cancellations. Client doesn't need to change for
  that.
- **"Restore purchases" flow** — if a user reinstalls and has an
  active subscription, tap Restore to re-verify against the server.
  Not strictly needed for v1 credit packs (grant is one-off per
  purchase), but essential for subscriptions once we ship them.
  Trivial to add on top of this service — `InAppPurchase.instance
  .restorePurchases()` populates the stream with historical
  purchases and we can re-verify each.
